# Ledger 演进目标

> 本文记录已确认的长期演进方向和验收边界，不构成自动排期。任何演进都必须保持零插件核心流程独立成立。

## 1. 演进原则

1. **核心自洽**：项目初始化、账务、查询、修订、作废、统计、配置和存储不依赖插件存在。
2. **插件追加能力**：插件能够贡献类型、字段、服务、命令、通信绑定、配置、存储和初始化资源，但不接管核心不变量。
3. **数据可存活**：插件停用或卸载后，历史数据仍可读取、统计和导出。
4. **协议自然映射**：同一应用命令可在 HTTP、CLI、MCP 和 Web UI 中使用不同自然形态，但共享同一业务执行路径。
5. **显式扩展点**：新增扩展能力前，先定义输入、输出、错误、生命周期和卸载语义，避免泛用中间件侵入核心流程。

## 2. 当前基线

当前系统已经提供：

- 零插件账务闭环与统计。
- L1、L2、冷引导三种插件运行形态。
- 类型、字段、服务、事件、配置、存储、项目初始化和 UI 插件扩展。
- L1 热重载回滚、L2 worker 崩溃重启。
- 配置核心、Storage Core、整体导入导出。
- 应用命令能力目录，以及 HTTP REST / RPC、CLI、MCP 的绑定描述。

以下目标在此基线上逐步推进。

## 3. P0：插件贡献应用能力

### P0-1：插件应用命令贡献

插件可注册 `budget.evaluate`、`report.generate`、`import.bankCsv` 等应用命令，并自动进入 `commands.describe`。

验收：安装独立报告插件后，命令可被发现、调用和卸载；卸载后核心账务无变化。

### P0-2：协议绑定贡献

插件命令可以声明 CLI、HTTP 和 MCP 的绑定；HTTP 从描述编译 REST 路由，MCP 从描述发现 tool，CLI 使用声明的命令路径与说明。

验收：同一插件命令通过 REST、CLI 和 MCP 调用时，落入同一个 handler 并得到一致的错误码。

### P0-3：命令输入与输出描述

能力目录统一提供运行时校验 schema、JSON schema、说明和示例；协议适配器可以在必要时声明输入转换，例如 CLI 的十进制金额转换。

验收：新增命令不需要在 HTTP、MCP 和文档中手写彼此漂移的输入定义。

### P0-4：受限执行扩展点

增加显式 `preValidate`、`postCommit` 等扩展点。前置扩展只能在定义的上下文中返回校验结果；后置扩展通过领域事件处理已提交状态。

验收：扩展失败的错误模型、是否阻止提交和是否允许修改输入都有明确规则与测试。

### P0-5：命名冲突治理

检测 command name、HTTP method/path、CLI 子命令和 MCP tool name 冲突，并返回类型化诊断。

验收：冲突插件不会覆盖既有能力，也不会使宿主进入部分加载状态。

## 4. P1：配置、存储与初始化扩展

### P1-1：插件配置 schema 贡献

插件可声明默认值、schema、配置说明和变更策略。

验收：配置文件能被统一校验；插件读取配置前可获得合并后的默认值。

### P1-2：插件配置迁移

插件版本升级时可以迁移自身配置，并在失败时保留上一份有效配置。

验收：旧配置升级、回退和无效配置场景均可诊断与恢复。

### P1-3：配置变更策略

每个配置项声明 `live`、`plugin-restart` 或 `host-restart`，由消费方依据策略重建资源。

验收：配置热更新不会导致运行中数据目录、数据库连接或 worker 状态不一致。

### P1-4：插件存储迁移统一化

插件通过 Storage Core 注册 owner migration 和 Repository，不再依赖兼容 `db` 服务管理新表结构。

验收：插件升级、重装、整体导出和整体导入后，插件数据结构可验证并可恢复。

### P1-5：插件数据集声明

插件声明自身数据集、schema version、导出、导入和完整性校验。

验收：未安装插件的数据仍被整体备份保留；重新安装后可继续接管数据。

### P1-6：初始化结果与回滚

`ledger init` 输出每个初始化器的状态，并区分已完成、可重试和失败状态。

验收：初始化中断后再次执行可安全继续，核心 `.ledger/` 资源保持可用。

### P1-7：L2 初始化协议

若 L2 插件需要项目初始化，改为声明式初始化请求并由主进程执行，不传递 worker 函数引用。

验收：worker 插件可请求受控项目资源，且宿主仍能管理错误和重试。

## 5. P2：组合、兼容性和可维护性

### P2-1：manifest 版本约束

manifest 声明所需核心版本、`plugin-contract` 版本、依赖插件及版本范围。

### P2-2：依赖求解与诊断

区分 required 与 optional dependency，输出依赖树、兼容状态和加载阻塞原因。

### P2-3：服务版本化

服务名或服务契约声明兼容范围，防止 provider 升级破坏 consumer。

### P2-4：L2 服务 RPC

为 worker 插件提供受控跨线程服务协议，替代直接传递对象引用。

### P2-5：插件健康状态

记录启动时间、崩溃次数、最近错误、重启次数、配置状态和初始化状态。

### P2-6：原子安装与升级

新版本先校验、暂存和激活，成功后切换；失败时保留可用版本。

### P2-7：插件测试工具包

提供内存 kernel、临时项目、Storage Core fixture、命令目录和 HTTP/MCP 适配器测试工具。

### P2-8：开发者文档生成

从能力目录、配置 schema 和 manifest 生成插件 API、REST、CLI 和 MCP 文档。

验收：升级失败、依赖缺失、worker 崩溃、配置错误和服务不兼容均可定位并安全降级。

## 6. P3：生态能力

### P3-1：插件包元数据

增加作者、仓库、许可证、变更记录和兼容矩阵。

### P3-2：插件来源与锁文件

支持可重复安装指定插件版本，记录来源和完整性摘要。

### P3-3：导入器框架

银行、支付平台和 CSV 导入器共享预览、映射、去重、提交和回滚协议。

### P3-4：报表与自动化框架

报表、预算、规则引擎和定时任务通过应用命令贡献接入系统。

### P3-5：生态安全能力

开放给不可信第三方插件时，再引入签名、权限与沙箱设计。

## 7. 推荐顺序

```text
插件命令贡献
  → 协议绑定贡献
  → 配置 schema 与存储迁移
  → 依赖、版本与健康治理
  → 原子安装与测试工具
  → 导入器、报表与自动化
  → 生态安全能力
```

最优先完成 P0。完成后，插件可以独立交付完整业务能力，而不局限于贡献类型、字段和服务。
